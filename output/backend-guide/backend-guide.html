Privy is the proof

The API verifies the token signature, issuer, audience, and expiry. The client cannot just send an arbitrary user ID and become that person.

One unique auth_subject maps to one local user.

Profile

Role is a field

username and role are both empty before onboarding, and both populated after it. There is no separate onboarding-completed timestamp.

A Captain can also participate in another Captain’s fund as Crew.

Availability

Fast check, final constraint

A Bloom filter can quickly rule out an occupied username. A possible match, stale index, or Redis failure falls back to SQL. The unique database constraint settles races.

New names: 3–24 lowercase letters, digits, or underscores; begin with a letter. Legacy names are preserved.

Settings and profile assets

Profile edits use PATCH /v0/me. Photos upload to a private S3 staging location, are processed by Sharp, and become published assets behind CloudFront. The backend checks ownership before attaching them to a user. Support requests are saved in SQL; there is no connected email or native push delivery provider.

03 · Where the state lives

The database is the memory.

PostgreSQL holds identities, balances, funds, orders, and payment evidence. Redis helps with speed and delivery; it does not replace the financial records.

04 · The app’s doorway

Ask. Validate. Respond.

Choose an endpoint to see what the app sends and what the backend returns. Request schemas come from the registered Fastify routes. Response examples were captured by calling the real handlers with synthetic fixtures.

Money is a string

Send decimal amounts like "12.345678". This avoids floating-point rounding. SQL uses exact decimal storage; token amounts use six decimal places.

Retries need a key

An Idempotency-Key makes supported retries reuse the earlier result. Reusing the same key with another operation or payload is rejected.

Accepted ≠ completed

An order returns 202 PENDING; the worker fills or rejects it later. Errors use {error, message}. Event/chat/inbox cursors and order UUID cursors are different contracts.

05 · Receiving funds

The QR requests a payment.
The chain proves it.

Creating a QR never adds money. The API credits the account only after checking a finalized Solana transaction against the expected test USDC mint, destination, amount, and payment reference.

What must match?

Finalized success · exact mint · treasury token account · six-decimal amount · reference attached to the intended transfer · actual token balance movement.

A signature is claimed globally across deposit paths. The credit and receipt are written atomically.

Pending and interrupted

The worker runs inside the API process. Persistent leases and paginated claiming let it recover after restarts. RPC failures keep the payment pending rather than inventing a credit.

Expired and repeated

QR requests expire after 30 minutes, but late payments still get checked hourly. Multiple distinct valid payments can credit one intent; the same transaction cannot credit twice.

Devnet only

The custom six-decimal SPL token is test USDC. Its legacy environment setting is USDG_MINT. Funding endpoints need token configuration. Other networks and Android wallet handoff are not implemented.

Creating a QR does not link the payer’s outside wallet to Privy. Linked-wallet deposit preparation, deposit claims, and withdrawals are separate API flows. Never describe a devnet test-token balance as mainnet USDC.
06 · Prices, orders, and background work

A paper trade has a lifecycle.

The ingestor brings prices in. The API accepts an instruction. The worker applies it later. Price data is real market data in normal operation; fills are simulated.

A conversation between services

The two background loops

Ingestor: takes a PostgreSQL leader lock; fetches Jupiter prices about every five seconds and token metadata every minute. Shared quotas constrain upstream requests. Solana price source times use a mainnet RPC, separate from devnet funding.

Worker: runs roughly every two seconds: value funds → process orders → finish trials → assess fees → deliver outbox notifications.

Order execution: waits at least three seconds and needs a fresh price observation. It rechecks permissions, policy, cash, and exposure. Stale data can block execution.

Truthful charts

Missing or stale prices are marked unavailable. Tracking a discovered token does not automatically make it tradable. Current trading instruments are SOL, JUP, JTO, and BONK; USDC is the quote asset.

Events and notifications

Fund events explain joins, orders, and fills. The outbox records work for later delivery into the notification inbox. SSE and WebSocket routes provide live data channels.

Access matters

Fund ownership controls trading. A Captain role alone does not permit trading someone else’s fund. Public performance and order history do not expose another user’s private available cash.

Current paper fund rules: a Captain seeds 1,000 USDC of app balance; one active or frozen fund per Captain; a 30-day trial. These are backend simulation rules, not the Anchor program’s 250 USDC minimum or annual member-fee design.

Accounts are on-chain state

These are Solana account layouts, not PostgreSQL tables. Fund-owned associated token accounts hold assets. Share tokens are nontransferable and support a permanent delegate.

Instructions change that state

Trade control

Swaps use allowlisted venues through CPI. The program checks token movement, minimum output, oracle freshness, slippage, exposure, and authority. Default autonomous trade and rolling daily budgets are 10% of NAV.

Policy and voting

Proposal state stores a hash; execution needs the matching route bytes. Passing requires more than half of the recorded supply. Vote weight uses shares at voting time, not an immutable holder snapshot.

Entry and exit

Captain seed minimum: 250 USDC. Captain ownership normally stays at least 5% with other members. Exits return pro-rata holdings rather than automatically selling everything into USDC. Fees take 10% of new profit above a member’s high-water mark.

What still needs engineering before connecting real capital

The integration gap

The API would need transaction building, signing, chain confirmation, on-chain state indexing, and reconciliation with the app’s views. Current paper IDs, rules, and accounting cannot simply be treated as on-chain funds.

Deployment, configured token/venue registries, oracle feeds, keeper operation, and environment-specific verification must also be established.

Known code limits

The repository documents OpenSeas/T3 price and loss-compensation caveats. T3 needs keeper-supplied Switchboard marks; Captain exits with T3 and remaining members can require fresh prices. Perpetual/prediction adapters, T3 TWAP, linked-wallet graph, discovery fee splits, and multisig admin rotation are not built.
